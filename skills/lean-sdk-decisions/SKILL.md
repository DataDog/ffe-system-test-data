# Maintain the central SDK decision contract

Use after `lean-sdk-feedback` has collected complete discussion and source evidence, or when a user explicitly resolves a contract choice. Keep workflow instructions in skills and product policy in the designated versioned contract repository. For FFE, use `DataDog/ffe-system-test-data`; inspect live instructions and the existing decision layout before writing. Create an isolated local proposal branch when requested, preserving other worktrees. Branch creation does not authorize a push.

Reuse stable decision IDs and preserve earlier revisions. Record the English rule, authority/evidence URLs, scope, accepted/proposed/conflict status, affected implementation owners, model/corpus mapping, native obligations and supersession history. A source-verified SDK outcome establishes that SDK's behavior; it does not approve fleet policy. Do not import a retrospective POC baseline as accepted main. Explicit prior user decisions remain authoritative within their scope; a new reviewer preference alone does not supersede them.

Give every decision a current PR link, preferably the exact comment in the thread where its current wording was last set or reaffirmed by the relevant authority. Keep original sources and superseded settings in provenance; do not select a source merely because it is the newest comment. Record who set it, when, the applicable scope/revision and known source SHA. Label reviewer proposals and author intent accurately. If a rule was set only in local discussion or inferred from source, retain the PR context link and explicitly mark the missing public decision-setting thread; never invent acceptance or publish a comment merely to fill the field.

Maintain a separate append-only, linked historical table of where each decision was tested. Include decision ID/revision or an explicit unversioned expectation profile, PR/thread, tested source SHA, patch/adapter/contract hashes when available, check, result, evidence kind and limits. Preserve failures, partial passes, superseded expectations and coverage gaps as well as successes. Distinguish comment dates from execution dates; leave unknown values explicit. Link decisions to table rows and rows to saved evidence. Reviewer-reported checks, historical local receipts, fresh native runs, model proofs and deployment observations are different evidence kinds. Later validation does not move the decision-setting link; later semantic changes do not upgrade old receipts. Update the current source and append history when an authorized new decision or test supplies new evidence.

For conflicting behavior, retain a minimal distinguishing input and each alternative's outcome. Separate malformed from absent, disabled provider from disabled opt-out, configured mode from effective policy, and parsing/preparation from evaluation-time error policy. Ask for a semantic choice only when necessary for dependent implementation; continue recording evidence, independent checks and non-conflicting work.

Ground the model in production before fan-out. Connect each rule to executable Lean definitions or explicitly mark it not modeled. Inspect statements and axioms, run an oracle and independent counterexamples, then compare actual native paths. Never call a proof of the model a proof of the SDK or treat finite corpus agreement as whole-program equivalence. Keep native lifecycle, nil handling, logging, concurrency, transport and performance evidence outside unsupported proof claims.

Freeze the exact English decisions, model, toolchain, corpus file inventory/IDs/counts and applicability profile with hashes. Bind target receipts to source SHA, adapter/patch hash and decision revision. An independently held manifest hash is required for trusted acceptance; hashes stored beside mutable inputs only establish consistency. A semantic revision invalidates earlier receipts for affected decisions. Implementers report contradictions centrally and cannot change their own acceptance baseline.

Produce a propagation plan by implementation owner and dependency, not one task per language label. Revalidate shared core before wrappers. Unknown, unapproved or conflicting decisions must not enter an accepted fleet bundle. Distinguish local proposal validation, central approval, native conformance, PR review, merge, release and deployed behavior. Reuse `lean-sdk-implement` and `lean-sdk-rollout` only for the corresponding authorized scope.

When publishing shared proofs for an authorized review reply, open or reuse a draft PR in `DataDog/ffe-system-test-data` containing the decision records, applicable Lean model/proofs, pinned manifest and linked validation history. Follow repository contribution requirements and the user's signing and push rules; keep the PR draft. After verifying the published revision, provide the draft PR URL and a direct permalink to the relevant decision's heading or lines at that commit. Pass both links to the SDK reply workflow, using linked short SHAs for commit references. Preserve the decision-setting thread as provenance and the historical test rows separately; a central draft PR does not confer fleet approval. Record the posted reply URL after readback so the evidence can be followed in both directions.

For an example, inspect `contracts/experimentation-opt-out/` on the FFE data proposal branch: D004 records the browser setting, scoped Go adoption and native validation, while preserving the earlier Go all-mode rejection and invalid-as-missing alternative in its history. D006 supersedes the earlier strict casing rule only in its recorded browser scope. Preserve those scopes when adapting another PR.

For operational decisions such as D017, encode the forbidden work as an observable model event as well as preserving return values. Exercise those events at the real native boundary and retain a negative control that restores the old behavior. Keep compiler evidence and uninstrumented timings separate: zero model/native calls do not prove lower runtime. The D017 example preserves mixed local timings and earlier CI regressions alongside the successful call-skip proof.
