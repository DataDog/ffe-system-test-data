# Contract and rollout ownership

Use `python3 scripts/plan.py bundle.json --slots 3` from this skill directory to validate pins, literal path ownership, and dependency ordering before dispatch. The coordinator's bundle contains `reviewed_profiles`, a mapping from accepted profile IDs to independently pinned manifest SHA256 values. Its `implementations` list contains objects with `id`, `targets` (language labels), `repository` (canonical owner/repo), `base_sha`, `contract_sha256`, `corpus_sha256`, `profile`, `profile_manifest_sha256`, `owned_paths` and optional `depends_on` (owner IDs). The helper rejects missing/unknown profiles, unreviewed profile hashes, overlapping ownership, unknown dependencies, cycles, mutable revision names and malformed pins. It produces a plan only; it does not execute workers or grant publication authority. Distinct repositories still require a reviewed dependency map; the helper cannot discover package aliases, validate the semantics of the reviewed profile or prove native conformance.

A contract bundle has a version and hash for English decisions, Lean definitions/theorem statements, trusted imports/toolchain, emitted corpus and applicability profile. Each requirement maps to an invariant or executable scenario, with explicit environmental assumptions and excluded behavior. CI should fail an unknown profile or missing required field rather than treat it as a default.

The coordinator owns the immutable baseline, dependency graph, task allocation and status ledger. Each worker owns only a native implementation/adaptation and native tests. An independent reviewer checks production reachability and correctness. A failed expectation is routed to the contract owner with a minimized trace; it is never automatically replaced by the SDK's output.

The output graph is repository/package based, not language based. Separate shared evaluation cores from exposure telemetry and platform wrappers: sharing one does not imply sharing the other. Pin vendored package versions and the downstream adoption commit. A wrapper may need no algorithm change but still needs adapter/lifecycle tests.

For CI, use deterministic bounded checks on PRs and larger generative/mutation jobs periodically. Model building happens centrally; SDK CI can consume an offline content-addressed corpus and run the actual native path. Keep a few independently authored examples and defect controls so a mistaken model/generator cannot silently redefine every expected result. Run existing tests alongside the new checks before proposing consolidation.
